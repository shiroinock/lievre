# AI エージェントからの使いやすさのベンチマーク

KEI を AI のコーディングエージェントが使うとき、どれだけ少ない量を読めば正しく書けるか。誤ったときに、型・lint・実行時のどこで気づけて、そのメッセージから直せるか。これを代表的な8つのデザインシステムと比べ、KEI の改善点を優先順に並べました。測定日は 2026-10-24 です。

## まとめ

- **改善前の KEI**：型で必須の props（`label`・`caption`・`title`・`description`）は強いものの、エージェント向けの入口がありませんでした。部品のふるまい（DataTable がどの行を並べ替えるか、Metric の `trend` が言葉を足すか）は型に書かれておらず、5課題中3課題で、エージェントがビルド済みの `lib/kei.js`（約5.8万トークン）を検索して実装を確かめていました。
- **このブランチで入れた改善**：型から生成する `llms.txt`、props の説明（TSDoc）、`foundation.d.ts` の肥大の解消（21.8KB → 2.3KB）、Badge の文字を必須に、`useToast` のメッセージに直し方を書く、`AGENTS.md`。
- **改善後の実測**：同じ5課題で、課題に使ったトークンは平均 14.3k → 8.4k（41% 減）、道具の呼び出しは平均 10.2 → 4.2 回、かかった時間は 45 → 24 秒になりました（各課題1回の計測で、改善前は準備の誤りで呼び出しが1〜2回多く出ています。「限界」を参照）。改善後は5件とも `llms.txt` だけを読み、型検査1回で通っています。
- **誤用の検出**：よくある誤り21件のうち、型・lint・実行時のどこかで止まるのは 14 → 15 件、メッセージから直し方まで分かるのは 10 → 11 件（63点満点で 37 → 40点）。残る6件は型では止められず、利用者向けの lint と開発時の警告が要ります（改善案の1と2）。
- **他システムとの比較**：KEI の弱点は、利用者向けの lint・実行時の警告・MCP や Skill の配布がないことです。強みは、課題あたりに読む量の少なさと、アクセシビリティに要る props を型で必須にしている点です。

## 方法

### 課題

[bench/agent/tasks.md](../bench/agent/tasks.md) の5件です。どのシステムでも同じ文で解けるよう、部品の名前ではなく画面の要件で書いています。

| 課題 | 内容                                                               | 主な部品                         |
| ---- | ------------------------------------------------------------------ | -------------------------------- |
| T1   | 設定画面：必須の入力・Switch・保存、空ならエラー、保存できたら通知 | TextField、Switch、Button、Toast |
| T2   | 請求書20件の表：金額と日付の並べ替え、10件ずつのページ送り         | DataTable、Pagination            |
| T3   | 削除の確認ダイアログ：キャンセルと危険な操作、削除後に通知         | Dialog、Button、Toast            |
| T4   | 申し込みフォーム：選択・ラジオ・同意のチェック、未入力にエラー     | Select、RadioGroup、Checkbox     |
| T5   | 稼働状況：稼働率の数値カードとサーバーの状態                       | Metric、Badge                    |

### 測るもの

1. **読む量**（[bench/agent/context.mjs](../bench/agent/context.mjs)）：課題を解くのに開く文書の大きさを、トークンの見積もり（英数字4文字か日本語1文字で1トークン）で数えます。KEI はパッケージに入る README と、使う部品を宣言している d.ts を丸ごと、または `llms.txt` だけ。他のシステムは、使う部品の Markdown 版の文書を `--external` で取得して数えます。
2. **誤用の検出**（[bench/agent/misuse.mjs](../bench/agent/misuse.mjs)、事例は [misuse-cases.mjs](../bench/agent/misuse-cases.mjs)）：エージェントがしがちな誤り21件を、利用側のアプリと同じ見え方（ビルド済みの `lib/` を通して）で型検査し、ESLint にかけ、jsdom で描画します。採点は1件3点です。
   - 型か lint で止まる：2点。編集のたびにエディタ（LSP）や検査で分かります。
   - 実行時に止まる（例外・`console.error`・`console.warn`）：1点。
   - どこでも止まらない：0点。
   - 最初のメッセージに直し方の言葉（`onCheckedChange`・`danger` など、事例ごとに決めたもの）が含まれる：1点を足す。
3. **エージェントの実測**（KEI のみ）：課題ごとに利用側のアプリを scratch に作り、パッケージ（`npm pack` したもの）だけを入れて、サブエージェントに [agent-prompt.md](../bench/agent/agent-prompt.md) の指示で解かせます。記録するのは、サブエージェントの合計トークン、道具の呼び出し回数、型検査の回数、読んだファイルです。合計トークンにはシステムの指示も入っているため、何も調べずに1行書くだけの対照（T0）の値を引いて比べます。

### 採点表（16点満点）

| 観点                                | 2点                                 | 1点              | 0点    |
| ----------------------------------- | ----------------------------------- | ---------------- | ------ |
| 文書の入口                          | llms.txt と部品の文書が単独で使える | どちらか一方     | なし   |
| MCP                                 | 公式で props や例を返す             | 非公式・検索だけ | なし   |
| props の説明                        | TSDoc と既定値                      | 型だけ           | 型なし |
| a11y の props を型で必須            | 名前・ラベルを必須                  | 一部             | なし   |
| 利用者向け lint                     | 公式で直し方付き                    | リポジトリ内だけ | なし   |
| 開発時の警告                        | 直し方付き                          | 少数             | なし   |
| 課題あたりの文書量（T1〜T4 の平均） | 5k トークン未満                     | 5k〜15k          | 15k 超 |
| エージェント向けの指示              | 利用者向けに配布                    | 貢献者向けのみ   | なし   |

### 1. 利用者向けの ESLint プラグイン

今の独自ルール（`kei/unit-outside-mono`）は `eslint.config.mjs` の中にあり、パッケージを使う側には届きません。ルールをプラグインとして切り出してパッケージに入れ、次のルールを足します。メッセージには直し方を書きます（いまのルールと同じ方針）。

- `button-type-in-form`：`<form>` の中の Button に `type` がない。「フォームの送信には type="submit" を付けてください（Button の既定は type="button"）」。
- `table-sort-before-page`：DataTable の `rows` に `.slice(` の結果を渡しているのに `sorting` がない。「全件を並べ替えてから区切り、sorting / onSortingChange で状態を持ってください」。
- `metric-unit`：Metric の `value` の文字列が `%` や `円` で終わる。「単位は unit に分けてください：value="99.95" unit="%"」。
- `dialog-close`：Dialog の `footer` にある Button が `onClick` を持たず、DialogClose にも包まれていない。

→ `lint/` に入れ、ESLint・Oxlint・Biome で使えるようにしました（README の「lint」）。誤用ベンチは 40 → 48 / 63 点です。`table-sort-before-page` は、`slice` のような汎用のメソッドを見張る形では流し込み方が増えるたびに直すことになるため外しました。代わりに DataTable にページ分け（`pageSize`）とサーバー任せの形（`dataMode="server"`）を持たせ、誤った順番を書けない作りにしました。lint は、並べ替えのある DataTable と Pagination を同じファイルで使い、DataTable のページ分けを使っていない組み合わせだけを見る `table-pagination` にし、誤用ベンチは 51 / 63 点です。`dialog-cancel-not-close` は、例が `open` だけを渡しているため、先に「onOpenChange を渡す」の指摘が出て、DialogClose の言葉までは届きません。

### 2. 開発時の警告

- KeiProvider の外で部品を描画したら警告する。いまは文脈の既定値で黙って動くため、どこにも現れません。Mantine は Provider がないと直し方付きの例外を投げます。
- Metric の `value` に単位らしい文字が入っていたら警告する（lint で拾えない動的な値のため）。
- 警告は開発時だけ出します。`lib/` のビルドで `process.env.NODE_ENV` をどう扱うかを先に決める必要があります。

### 3. 型の誤りのメッセージ

`SwitchProps` や `Tone` のような名前付きの型は、誤りのメッセージに名前しか出ません。次のどちらかで、メッセージに使える名前が出るようにします。

- 取り違えやすい props を明示的に禁止し、説明を付ける（例：`onChange?: never` に「onCheckedChange を使います」）。補完と hover に説明が出ます。メッセージの文面がどう変わるかは、試して確かめる必要があります。
- 値の候補が少ない型（`Tone`）は、props の中で展開して書く。

### 4〜8

- **plugin（Skill）**：SmartHR UI は Claude Code の plugin marketplace で部品のガイドラインを配っています。KEI は `llms.txt` と、レビューの観点（本文の「約束」と「確かめ方」）を Skill にして配れます。
- **使い方の例**：T2 の改善後の解答は、`llms.txt` にある並べ替えとページ送りの例をほぼそのまま使っていました。Story の play 関数のある例から、部品ごとに1つずつ抜き出して載せると効きます。
- **索引への分割**：Mantine や Chakra は `llms.txt` を索引にして、本文を部品ごとに分けています。KEI の `llms.txt` が1万トークンを超えたら同じ形にします。
- **MCP**：Primer の MCP は使い方とアクセシビリティの指針を返すツールを持っています。KEI では、部品が少ないうちは `llms.txt` を読むほうが安く、効果は小さいと見ています。
- **CI**：`npm run bench:agent` は数秒で終わります。誤用の点数が下がったら止める検査にできます。

## 再実行の手順

```sh
npm ci
npm run bench:agent                                   # 誤用の検出と、KEI の読む量
node bench/agent/context.mjs --external               # 他のシステムの文書も取得して数える
node bench/agent/misuse.mjs --json out.json           # 結果を JSON で残す
```

改善前と比べるときは、別のチェックアウトを `--root` で渡します。

```sh
git worktree add ../kei-main main
cd ../kei-main && npm ci && npm run build:lib && cd -
node bench/agent/misuse.mjs --root ../kei-main
node bench/agent/context.mjs --root ../kei-main
```

エージェントの実測は手作業です。

1. `npm run build:lib && npm pack` でパッケージを作る。
2. 課題ごとに空の利用側アプリを作り、パッケージ・react・react-dom・typescript を入れる（`npm run typecheck` が `tsc --noEmit` を呼べること）。`src/App.tsx` は KeiProvider と ToastProvider で包むだけ。
3. [agent-prompt.md](../bench/agent/agent-prompt.md) に課題の節を入れてサブエージェントに渡す。同じモデルで、対照の T0（何も調べずに1行書く）も1回解かせる。
4. 合計トークン・道具の呼び出し・時間・読んだファイルを [results/agent-runs.json](../bench/agent/results/agent-runs.json) の形で残し、解答が型検査を通り、課題の確認項目を満たすかを見る。

今回の結果の JSON は [bench/agent/results](../bench/agent/results) にあります。

## 限界

- エージェントの実測は1モデルで各課題1回です。トークンの差は数千で、ばらつきと同じくらいの大きさがありえます。道具の呼び出し回数と、実装を読みに行ったかどうかのほうが差がはっきりしています。
- トークンは文字数からの見積もりです。システム同士の比較には使えますが、実際の課金の値ではありません。
- 他のシステムには課題を解かせていません。文書の量と提供物から見積もっています。ラジオ・チェックボックスの文書を数えていないため、T4 は少なめです。
- 誤用の事例は KEI の API に合わせて選んでいます。「直し方が分かる」は、メッセージに決めた言葉が入るかどうかの機械的な判定です。
