# KEI を端末（TUI）に広げる道

KEI のデザイン言語を、端末の画面にも広げるための比較です。試作は [spikes/tui](../spikes/tui/README.md) にあります。本体（`src/`・ルートの `package.json`）には入れていません。

## 推奨

1. **パッケージ**：このリポジトリを npm のワークスペースにして、`@kei-design/tokens`・`@kei-design/react`・`@kei-design/tui` の3つに分ける。先にトークンだけを分け、端末向けの値（256色の番号など）も `tokens/terminal.json` として書き出す。Go や Rust の実装は、必要になったときに別のリポジトリで作り、この JSON を読む。
2. **言語とフレームワーク**：Ink 8（React で書く）。Web と同じ TypeScript と React で書けて、スクリーンリーダー向けの出力が組み込みである。弱いのは、East Asian Width が曖昧な文字の幅を設定できないこと。
3. **書体**：標準の罫線とブロックの文字を基本にする。私用の領域（PUA）に字を入れた書体「KEI Term」は、利用者が選んだときだけ使う。中身は、Unicode にない形（ボタンの丸い端とフォーカスの輪）に限る。枠の線は Unicode の罫線のままにする。多くの端末が罫線を自前で描くからで、書体で描いた線はセルの境目に継ぎ目が出た（下の「書体」を参照）。
4. **色**：truecolor は Web と同じ値で、同じ検査をする。256色は、コントラストを保てる中でいちばん近い色に落とす。16色では、KEI は面を塗らない。文字は端末の色のままにし、強調は反転表示で示す。色を付けるのは記号だけにする。

## 1. パッケージの分け方

| 案                                                  | 良い点                                                                                                                                                                              | 困る点                                                                                                                      |
| --------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| **A. このリポジトリをワークスペースにする**（推奨） | トークンの正（`kei.css`）と書き出し（`tokens.json`）が同じ変更に入る。いまある「書き出し忘れを `npm test` が止める」仕組みが、端末向けの値にもそのまま効く。DESIGN.md も1か所で済む | ルートの `package.json`（いまは `@kei-design/react` そのもの）を `packages/react` へ移す手間がかかる。CI も分ける必要がある |
| B. TUI だけ別のリポジトリにする                     | 依存と CI が完全に分かれる                                                                                                                                                          | トークンを変えるたびに、公開してから向こうを上げる必要がある。コントラストの検査も2か所に分かれる                           |
| C. いまの1パッケージに TUI も入れる                 | 手間が最も少ない                                                                                                                                                                    | Web の利用者に Ink と yoga-layout が入る。`exports` で分けても、依存は分けられない                                          |

**A を2段階で進めます。**

1. いまの `scripts/build-tokens.mjs` に、端末向けの書き出しを足す。中身は、テーマごとの役割、truecolor の値、256色の番号、16色の役割（反転か記号の色か）。試作の `spikes/tui/src/palette.ts` の `quantize()` がその計算をしている。
2. TUI の部品が試作を超えたら、`packages/tokens`・`packages/react`・`packages/tui` に分ける。`@kei-design/tokens` には JSON と CSS の変数だけを入れ、依存は持たせない。

Go と Rust の実装は、使う場面が出てから別のリポジトリで作ります。`terminal.json` を読めばよいので、色の計算を言語ごとに書き直さずに済みます。

## 2. 言語とフレームワーク

| ---------------------- | ---------------------------------------------------------------------------------------------- | ---------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| KEI との近さ           | 部品・props・`/** */` の説明・lint の考え方をそのまま使える。React の Context でテーマを渡せる | Elm 型の Model と Update と View。部品の書き方は別物になる | 即時モードの描画。部品は Widget の trait になる                                      |
| 枠と配置               | Yoga（Flexbox）。`borderStyle` に自前の字の組を渡せる                                          | Lip Gloss の Style（枠・余白・寄せ）。字の組を自前で渡せる | Layout の制約。Block の枠の字を自前で渡せる                                          |
| 色の段階               | chalk 任せ。段階は `chalk.level` で上書きできる（試作はこれで KEI の判定に合わせた）           | `colorprofile` が判定して自動で落とす。いちばん揃っている  | 段階を落とす仕組みは自前で書く                                                       |
| 明るい背景か暗い背景か | なし（試作では OSC 11 で問い合わせた）                                                         | `HasDarkBackground` がある                                 | なし（crate を足すか自前）                                                           |
| スクリーンリーダー     | `INK_SCREEN_READER` で、役割と状態を添えた線形の出力に切り替わる。`aria-hidden` で飾りを隠せる | 組み込みはない                                             | 組み込みはない                                                                       |
| 幅の計算と曖昧な文字   | `string-width` が曖昧な文字を1セルとして数える。変える口がない                                 | 未確認                                                     | `unicode-width`。crate には CJK 向けの幅の関数があるが、Ratatui から選べるかは未確認 |
| 配り方                 | npm。Node.js が要る                                                                            | 1つの実行ファイル                                          | 1つの実行ファイル                                                                    |
| 依存                   | 23（yoga-layout、react-reconciler など）                                                       | Go のモジュール                                            | crate                                                                                |

**Ink を推奨します。** 理由は3つです。1つ目は、KEI の部品と同じ言語と同じ考え方で書けること。2つ目は、トークンを JSON で受け渡す層すら要らず、`tokens.json` をそのまま読めること。3つ目は、スクリーンリーダー向けの出力があることです。WCAG AA を必ず守る KEI では、3つ目の差が大きい。

Ink の弱点は2つあります。1つは曖昧な文字の幅で、試作では `KEI_AMBIGUOUS=wide` のときに ASCII の字の組へ切り替えて避けました。もう1つは Node.js が要ることです。1つの実行ファイルで配りたい道具には Go が向きます。その場合も、`terminal.json` を読んで Lip Gloss の Style を作れば、同じ見た目になります。

## 3. 書体

端末では、書体を決めるのは利用者です。アプリの側から、いまどの書体で描かれているかを知る方法はありません。

| 案                                                        | 良い点                                                                                                                                         | 困る点                                                                                                                                                                                                                  |
| --------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **標準の文字だけで描く**（U+2500〜、U+2580〜、U+1FB00〜） | 何も入れずに、どの端末でも出る。kitty・WezTerm・Ghostty・Windows Terminal・xterm.js（WebGL）は罫線を自前で描くので、線がセルの境目で途切れない | 角の丸みは `╭` の1種類しかない。ボタンの丸い端はない。U+1FB00〜（Symbols for Legacy Computing）は、自前で描かない端末では、入っていない書体が多い                                                                       |
| **私用の領域に字を足した書体（KEI Term）**                | 角の丸み、線の太さ、ボタンの端、フォーカスの輪を KEI に合わせて作れる                                                                          | 書体が入っていないと豆腐（□）になる（`out/*-no-font.png`）。入っているかを確かめる手段がないので、利用者が選ぶ形にしかできない。書体で描いた線は、セルの境目に継ぎ目が出る（`out/truecolor-*-kei-term.png` の枠の上下） |

**標準の文字を基本にし、KEI Term は利用者が選んだときだけ使います**（`KEI_GLYPHS=kei-term`）。KEI Term に入れるのは、Unicode にない形だけにします。

- ボタンの丸い端（U+E506・E507）：セルを埋め、外側の角だけを丸めた形。前景色をボタンの色にして描く。
- フォーカスの輪（U+E508・E509）：ボタンの端から約3px（16px のとき）離した細い括弧。Web の `outline-offset` に当たる。

試しの書体には、角と辺（U+E500〜E505）も入れました。比べてみると、線の継ぎ目が出て、罫線を自前で描く端末に負けます。このため、枠は標準の罫線のままにします。

### 私用の領域の範囲

**U+E500〜U+E53F** を使います。Nerd Fonts 3.5.1 は、基本多言語面の私用の領域を U+E000〜E00A、E0A0〜E0D7、E200〜E2A9、E300〜E3E3、E5FA〜E6BB、E700〜E958、EA60〜EC84、ED00〜F385、F400〜F533 で使い、第15面（U+F0001〜F1AF0）に Material Design のアイコンを置いています。U+E3E4〜E5F9 は空いているので、Nerd Font と KEI Term を並べて使っても重なりません。

第16面（U+100000〜）も空いています。ただし、古い端末の中には、基本多言語面の外の字の扱いを誤るものがあります。そのため、まずは基本多言語面に置きます。Nerd Fonts の今後の版でこの範囲が埋まらないかは、版を上げるたびに `glyphnames.json` で確かめる必要があります（試作の `font/build.py` の注記に書いてあります）。

### 入れていない端末での見え方

字の組は利用者が選びます（`KEI_GLYPHS=unicode | kei-term | ascii`）。何も選ばなければ標準の文字です。KEI Term の字は、選んだときだけ出ます。

- 標準の文字の組では、ボタンの端は背景色を塗った空白、フォーカスの輪は `▏` と `▕`（1/8 の縦線）になる。
- `TERM=dumb` か、曖昧な文字を全角にする端末（`KEI_AMBIGUOUS=wide`）では ASCII（`+ - | [ ] >`）にする。

### 元にする書体

試しの書体は、リポジトリにすでにある `@fontsource/ibm-plex-mono` の Latin の字に、10字を足して作りました。配るときは PlemolJP（v3.1.0）を元にするのがよいと考えます。日本語と罫線が入っていて、半角と全角がはじめから 1:2 だからです。

ライセンスは、Plex も PlemolJP も OFL 1.1 です。予約されている名前「Plex」は使えないので、「KEI Term」とします。PlemolJP の側で予約されている名前があるかは、配る前に確かめます。`scripts/wear/font.py`（`claude/kei-wear-age` の枝にある）と同じく fontTools で変形し、送り幅が1セルであることと、名前に「Plex」が入らないことを `font/build.py check` で検査します。

## 4. KEI の約束の移し方

| 約束                   | 端末での守り方                                                                                                                                                                                                                                                                                    |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 読める大きさ           | 文字の大きさは利用者の端末が決めるので、アプリは変えない。KEI の側でできるのは、太字を見出しと主な操作だけに絞ること、薄い文字（`dim`）を使わないこと。薄い文字は、端末によって色が変わり、コントラストを保証できない                                                                             |
| 色は役割で使う         | ウルトラマリン（`accent`）は「押せる・選んでいる」だけに使う。緑・黄・赤は状態だけ。状態は記号と言葉の両方で示す（`✓ 正常`・`! 注意`・`✕ 停止`）。16色では言葉は端末の文字の色のままにし、記号だけに色を付ける                                                                                    |
| 面と線で階層をつくる   | truecolor と 256色では、カードの面（`surface`）と表の見出し（`surface-sunken`）を塗る。線は1セルの罫線で、`border-strong` を使う（Web の `border` は 1.3:1 と弱く、端末の細い線では面の差が潰れるため）。影は使わない。フォーカスは必ず見せる（`▏ ▕` か KEI Term の輪、16色と色なしでも字で示す） |
| 数値は比べられるように | 端末では英数字がもともと等幅なので、桁は右に揃えて、小数の桁数を固定するだけで揃う。単位は見出しに書く（`平均（秒）`）。増減は言葉でも書く（`前月より 4.2% 増`）                                                                                                                                  |
| 英数字と日本語を 1:2   | 端末では、セルの格子がこの決まりそのものになる。半角は1セル、全角（East Asian Width が W と F）は2セル。余白も同じ比で考え、横2セル≒縦1行≒1em とする（カードの内側は上下1行・左右2セル）                                                                                                          |

### 全角と曖昧な文字

- 全角（W・F）は2セル。幅の計算には `string-width` を使う（Ink も同じものを使う）。
- **East Asian Width が A（曖昧）の字は、端末の設定で1セルにも2セルにもなる。** 罫線（U+2500〜）、ブロックの文字の多く（`▌▏▕█`）、`○●▲▼→×…①` が A です。私用の領域（U+E000〜F8FF、第15面・第16面）も A です。日本語の端末では2セルにする設定が珍しくなく、そうすると枠が崩れます。
- 方針：
  - 枠と区切り以外では A の字を避ける。状態の記号は N（中立）の `✓`（U+2713）と `✕`（U+2715）、それに ASCII の `!` を使う。`×`（U+00D7）や `●` は使わない。
  - 枠には A の字を使うしかない。曖昧な文字を全角にする端末では、利用者が `KEI_AMBIGUOUS=wide` を指定し、ASCII の組に切り替える。Ink には曖昧な文字を2セルと数えさせる口がないので、字を替えて避ける。
  - U+1FB00〜 の字（`🭼` `🭽` など）は N なので、幅は崩れない。ただし書体が入っていない端末が多いので、今回は使わない。

## 5. 色とアクセシビリティ

### 色の段階

| 段階      | 判定                                    | 描き方                                                                                                                                                                                         |
| --------- | --------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| truecolor | `COLORTERM=truecolor` か `24bit`        | Web と同じ値。Web と同じ組み合わせを、同じ基準（文字 4.5、部品と輪郭 3）で検査する                                                                                                             |
| 256色     | `TERM` に `256` を含む                  | 16〜255番だけを使う（0〜15番は利用者のテーマで値が変わる）。まず面の色をいちばん近い色に落とす。次に、前景の色を「組む背景のすべてに対して基準を満たす中で、OKLab でいちばん近い色」に落とす   |
| 16色      | それ以外の端末                          | 値が分からないので、KEI は面を塗らない。文字は端末の色のまま。主なボタンは反転表示（コントラストは利用者の文字と背景そのもの）、ほかのボタンは下線。色は状態の記号とフォーカスの輪だけに付ける |
| 色なし    | `NO_COLOR`、`TERM=dumb`、端末でない出力 | 色を付けない。太字・下線・反転は残す                                                                                                                                                           |

`NO_COLOR` と `FORCE_COLOR` が両方あるときは、次の順に判断します（`palette.ts` の `detectLevel()`）。

- `FORCE_COLOR=0`・`1`・`2`・`3` のように段階まで指定されていれば、それに従う。
- そうでなければ、`NO_COLOR` が優先する。

chalk は `FORCE_COLOR` を優先するので、KEI が段階を決めたあとで `chalk.level` を上書きします。

256色に落とした結果は、Paper と Ink の両方で、13の組み合わせがすべて基準を満たしました（`spikes/tui/out/contrast.md`）。Ink の面（`#11143A`）は、近い色がない紺なので、灰色の `#1C1C1C` になります。色みが変わる点は、トークンの側で256色向けの値を指定できるようにするかを、あとで決めます。

### 明るい背景と暗い背景

Paper は明るい背景の端末に、Ink は暗い背景の端末に当てます。決め方は次の順です。

1. `KEI_THEME=paper|ink` で指定されていれば、それに従う。
2. OSC 11 で端末の背景色を問い合わせる。xterm・iTerm2・kitty・WezTerm・Ghostty・Windows Terminal が答える。試作では 150ms 待つ。
3. `COLORFGBG` を見る。
4. どれも分からなければ Paper にする。

KEI が塗るのは自分の面（カード・表・ボタン）の中だけです。面の外の文字は端末の色のままにします。こうすると、テーマの判定を誤っても、面の外の読みやすさは損なわれません。面の中は KEI の値どうしで検査済みです。

### スクリーンリーダー

端末の画面を読む人は、VoiceOver と Terminal.app、NVDA と Windows Terminal などを使っています。どれも画面の文字をそのまま読むので、画面全体を描き直す TUI は読みにくくなります。

- Ink の `INK_SCREEN_READER=true`（`isScreenReaderEnabled`）では、枠を描かずに、役割と状態を添えた線形の出力にする（`spikes/tui/out/screen-reader.txt`）。KEI の部品は `aria-role` と `aria-state` を必ず持つ。
- 罫線のような飾りは `aria-hidden` にする。読ませると「罫線 横」が何十回も続く。
- 表の Box に `aria-label` を付けると、Ink はラベルだけを読み、中の行を読まない。そのため表にはラベルを付けず、見出しの行を読ませる。
- フォーカスしている部品の位置に、端末のカーソルを置く（Ink の `useCursor`）。画面拡大や点字ディスプレイは、カーソルを追うものが多い。試作ではまだ置いていない。
- 状態は言葉で書き、記号だけにしない。回る印（スピナー）で行を何度も描き直さず、終わったら1行で結果を書く。
- Ink の `aria-state` には「フォーカス中」がなく、`selected` で代用した（「(selected) 保存する」と出る）。Ink に提案するか、KEI の側で言葉を足すかを、あとで決める。

## 試作で分かったこと

- Ink 8 の Box は、`borderStyle` に自前の字の組を、`borderBackgroundColor` と `backgroundColor` に面の色を受け取る。KEI の Card はそのまま書けた。
- `renderToString` で、端末なしに ANSI の出力を作れる。スナップショットのテストに使える。
- xterm.js の DOM の描画は、全角の字の幅が書体によって変わると、後ろの字を押し出す。WebGL の描画は格子を守る。スクリーンショットは WebGL の描画で撮った。
- 書体で描いた罫線は、WebGL の描画でもセルの境目に薄い継ぎ目が出る。枠を標準の罫線のままにする理由の1つ。

## 次にやること

- `scripts/build-tokens.mjs` で `tokens/terminal.json` を書き出し、256色の値をテストで検査する。
